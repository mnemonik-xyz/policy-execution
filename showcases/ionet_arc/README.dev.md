# io.net CaaS Pilot — Developer Runbook

Concise, developer-friendly guide for deploying and running the Whisper transcription worker on
io.net CaaS (Containers-as-a-Service) with Arc/Warrant.

---

## Key Terms and Identifiers

* **`WARRANT_WORKER_TOKEN`:**
  A secret Bearer token (at least 32 characters) generated by the operator before deployment and
  injected into the container via the `WARRANT_WORKER_TOKEN` environment variable. The worker
  HTTP service ([`worker.py`](worker.py)) validates this token on `POST /job` and `GET /job`.
  It protects your public worker endpoint from unauthorized access.

* **`DEPLOYMENT_ID`:**
  The unique deployment identifier assigned by io.net once the container is provisioned. It is
  returned in the `deploy` command response and stored in `artifacts/io-deployment.json` under
  the key `"deployment_id"`. You pass this ID to `caas_get_deployment_containers` to locate
  the container and to `destroy` to tear it down.

* **`PUBLIC_ENDPOINT`:**
  The public HTTPS hostname and port assigned by io.net's reverse proxy/ingress router mapping
  to your container's port `8080`. You obtain this by querying `caas_get_deployment_containers`
  after deployment (e.g., `container-xyz.io.net` or `x.x.x.x:port`).

---

## Important Things to Keep in Mind Before Deploying

* **CaaS vs. VMs (No SSH Keys Needed):**
  This showcase uses io.net **CaaS** (Containers-as-a-Service), not full Virtual Machines (IaaS).
  Do not create a VM in the io.net dashboard. No SSH keys are required or supported. Ingress is
  via HTTPS to port `8080`, authenticated by `WARRANT_WORKER_TOKEN`.
* **Hardware & Location IDs (Strings and Numbers Supported):**
  io.net returns both regional cluster IDs (such as `"gpu_1x_l40"` with location `"US"`) and
  network integer IDs. Both formats are supported by `adapter.py`:
  - Regional hardware: `"hardware_id": "gpu_1x_l40"`, `"location_ids": "US"` (or `["US"]`).
  - Network hardware: `"hardware_id": 12`, `"location_ids": [1]`.
* **5-Minute Estimate Freshness Window:**
  `adapter.py` rejects estimates older than 300 seconds (`observed_at`). Generate a fresh estimate
  immediately prior to running `deploy`.
* **Exact Resource Matching:**
  Resource fields (`hardware_id`, `location_ids`, `duration_hours`, `gpus_per_container`,
  `replica_count`) in `deploy-args.json` must match `price-args.json` byte-for-byte.
* **Preflight Budget Gate (`--usd-pointer`):**
  `--usd-pointer /data/data/total_cost_usdc` inspects the live estimate JSON. If the extracted
  price exceeds `--max-cost-usd`, deployment aborts before sending requests to io.net.
* **Duration Billing Only:**
  `adapter.py` rejects `billing_model: "payg"` because `duration_hours` does not bound a PayG
  container's lifetime. Use `"duration"`. Still run the teardown step immediately after
  transcription: the one-hour limit is a provider setting, not proof that charges stopped.

## Step-by-Step Deployment Runbook

### Step 1: Environment Setup

Set your io.net API key (with `io-cloud` scope) and activate the virtual environment:

```sh
export IO_NET_API_KEY="your-io-net-api-key"

python3 -m venv .venv
.venv/bin/pip install -r showcases/ionet_arc/requirements.txt
```

Verify tests pass locally:

```sh
.venv/bin/python -m unittest showcases.ionet_arc.test_pilot -v
```

---

### Step 2: Build and Push Worker Image

Run the **Build io.net Arc transcription image** workflow from GitHub Actions using
`workflow_dispatch`. It publishes `ghcr.io/mnemonik-xyz/warrant-transcription:pilot` for
`linux/amd64` with CUDA for GPU execution on io.net, plus the separate
`ghcr.io/mnemonik-xyz/warrant-transcription:pilot-arm64` image for CPU inference on Apple
Silicon Macs.

To build and push only the GPU image manually instead:

```sh
# Authenticate with GHCR (using a PAT with write:packages scope)
echo "$GITHUB_TOKEN" | docker login ghcr.io -u mnemonik-xyz --password-stdin

# Build and push native x86_64 image
docker buildx build --platform linux/amd64 \
  -t ghcr.io/mnemonik-xyz/warrant-transcription:pilot \
  --push showcases/ionet_arc
```

Ensure the repository visibility on GitHub/GHCR is set to **Public**, or obtain an image digest.

---

### Step 3: Discover Hardware and Balances

Inspect available hardware and existing account balance:

```sh
# Discover provider MCP tools and schemas
.venv/bin/python scripts/ionet-showcase.py discover --out artifacts/io-tools.json

# Query available GPU hardware
.venv/bin/python scripts/ionet-showcase.py read caas_get_hardware_ids \
  --out artifacts/io-hardware.json

# Check current credit balance
.venv/bin/python scripts/ionet-showcase.py read get_credit_status \
  --out artifacts/io-credit-before.json
```

Find an available GPU with an integer `hardware_id` (e.g. `12` for RTX 4090, `226` for L40S).

---

### Step 4: Get Price Estimate

Create `price-args.json` using the desired hardware and location IDs (e.g. `gpu_1x_l40` in `US`):

```json
{
  "hardware_id": "gpu_1x_l40",
  "location_ids": "US",
  "duration_hours": 1,
  "gpus_per_container": 1,
  "replica_count": 1
}
```

Request the estimate:

```sh
.venv/bin/python scripts/ionet-showcase.py read caas_get_price_estimate \
  --args price-args.json --out artifacts/io-estimate.json
```

---

### Step 5: Deploy Worker Container

1. Generate a random worker authentication token:
   ```sh
   WORKER_TOKEN=$(openssl rand -hex 24)
   echo "Worker token: $WORKER_TOKEN"
   ```

2. Create `deploy-args.json` with matching resources:
   ```json
   {
     "billing_model": "duration",
     "hardware_id": "gpu_1x_l40",
     "location_ids": "US",
     "duration_hours": 1,
     "gpus_per_container": 1,
     "replica_count": 1,
     "resource_private_name": "warrant-whisper-worker",
     "image_url": "ghcr.io/mnemonik-xyz/warrant-transcription:pilot",
     "traffic_port": 8080,
     "env_variables": {
       "WARRANT_WORKER_TOKEN": "<WORKER_TOKEN_VALUE>"
     }
   }
   ```

3. Deploy using the estimate and safety gate:
   ```sh
   .venv/bin/python scripts/ionet-showcase.py deploy \
     --args deploy-args.json \
     --estimate artifacts/io-estimate.json \
     --usd-pointer /data/data/total_cost_usdc \
     --max-cost-usd 1.00 \
     --state artifacts/io-deployment.json
   ```

   or run manually with the following command
   ```sh
   docker run --rm \
     --name warrant-transcription \
     --gpus all \
     -p 8080:8080 \
     -e WARRANT_WORKER_TOKEN="$WORKER_TOKEN" \
     ghcr.io/mnemonik-xyz/warrant-transcription:pilot
   ```

---

### Step 6: Query Endpoint and Submit Transcription Job

1. Inspect container details to retrieve the assigned public HTTPS ingress endpoint:
   ```sh
   .venv/bin/python scripts/ionet-showcase.py read caas_get_deployment_containers \
     --args '{"deployment_id": "<DEPLOYMENT_ID>"}' \
     --out artifacts/io-containers.json
   ```

2. Check health (`GET /health`):
   ```sh
   curl https://<PUBLIC_ENDPOINT>/health
   ```

3. Submit audio job (`POST /job`):
   ```sh
   AUDIO_FILE="audio.mp3"
   CHECKSUM=$(shasum -a 256 "$AUDIO_FILE" | awk '{print $1}')

   curl -X POST "https://<PUBLIC_ENDPOINT>/job?language=en" \
     -A "Mozilla/5.0" \
     -H "Authorization: Bearer $WORKER_TOKEN" \
     -H "Content-Type: application/octet-stream" \
     -H "X-Audio-SHA256: $CHECKSUM" \
     --data-binary @"$AUDIO_FILE"
   ```

4. Copy `job_id` from the submission response, then poll for transcription completion
   (`GET /job/<job_id>`):
   ```sh
   curl -H "Authorization: Bearer $WORKER_TOKEN" \
     "https://<PUBLIC_ENDPOINT>/job/<job_id>"
   ```

   Submit additional audio with `POST /job` as needed. Each distinct upload has its own
   `job_id`; `GET /jobs` returns all submitted jobs.

5. Read the container logs to follow job lifecycle events and GPU utilization. The worker emits
   JSON log records on startup, job start/end, and every 10 seconds while a job runs with
   utilization, memory, temperature, and power snapshots when `nvidia-smi` is available. Set
   `WARRANT_GPU_LOG_INTERVAL_SECONDS` to change the running-job cadence. It never writes the
   worker token, audio, or transcript text to these logs.

---

### Step 7: Teardown and Cleanup

Immediately terminate the container; do not wait for the one-hour duration to end:

```sh
.venv/bin/python scripts/ionet-showcase.py destroy \
  --state artifacts/io-deployment.json
```

Verify your credit balance after destruction:

```sh
.venv/bin/python scripts/ionet-showcase.py read get_credit_status \
  --out artifacts/io-credit-after.json
```

## Seller MCP container

[`Dockerfile.seller`](Dockerfile.seller) packages the seller MCP server
([`seller_mcp_server.py`](seller_mcp_server.py)) for the VM, behind Caddy, and for a laptop
smoke test. The image holds the seller modules, a Python 3.12 venv from
[`requirements.txt`](requirements.txt), and the `warrant-host` and `warrant-policy` binaries in
`/usr/local/bin`. It holds no `warrant-evidence`, `init.py`, keys or config: `init.py` runs on
the host, and config and keys are mounted at runtime.

### Build

The build context is the repository root. BuildKit is required. The legacy builder ignores
[`Dockerfile.seller.dockerignore`](Dockerfile.seller.dockerignore) and would send the whole
repository, `.keys/` included. With BuildKit the context is a few MB. `BIN_SOURCE=host` adds
the two release binaries, which carry debug info, so tens of MB.

```sh
# Laptop or CI (default BIN_SOURCE=build): compiles both binaries with RISC0_SKIP_BUILD=1,
# so no RISC Zero toolchain is needed.
DOCKER_BUILDKIT=1 docker build -f showcases/ionet_arc/Dockerfile.seller -t warrant-seller:dev .

# Linux VM only: copy target/release/warrant-host and target/release/warrant-policy, built on
# the host by the configure action with RISC0_USE_DOCKER=1.
DOCKER_BUILDKIT=1 docker build --build-arg BIN_SOURCE=host \
  -f showcases/ionet_arc/Dockerfile.seller -t warrant-seller:host .
```

* `BIN_SOURCE=build` is the default. The binaries it builds embed laptop guest image IDs. The
  seller never proves, so that does not matter for the seller.
* `BIN_SOURCE=host` is for the Linux VM only. On macOS `target/release` holds Mach-O binaries,
  which do not run in the image. When the binaries are missing, the build fails with
  `"/target/release/warrant-policy": not found`.
* The build runs both binaries once. A binary that does not run in the image (Mach-O, wrong
  architecture, missing library) fails the build at the step that greps for `Usage: warrant-policy`.
* Any other value fails with `load metadata for docker.io/library/bins-<value>`, because no
  stage `bins-<value>` exists.
* Never pass a secret as `--build-arg`. Secrets arrive only at runtime.

Check the binaries and the user:

```sh
docker run --rm warrant-seller:dev warrant-policy --help   # exits 1 and prints "Usage: warrant-policy ..."
docker run --rm --entrypoint id warrant-seller:dev -u      # 10001
docker run --rm --entrypoint cat warrant-seller:dev /usr/share/warrant-seller/pip-freeze.txt
```

The Linux binaries must match the host build. Run `warrant-policy hash` on a policy JSON that a
host test produced, and compare the hash:

```sh
docker run --rm -v "$PWD/policy.json:/tmp/p.json:ro" warrant-seller:dev warrant-policy hash /tmp/p.json
```

### Container user and paths

The container runs as UID/GID **10001**. The deploy role default `warrant_canary_seller_uid`
matches it. Secret files on the host must be owned by UID 10001 with mode 0600, and the state
directory on the host must be writable by UID 10001.

| Path in the container | Mount | Purpose |
| --- | --- | --- |
| `/app/showcases/ionet_arc/config` | read-only | Manifest, public keys, vendor credential and signature. The manifest's checkout-relative `public_files.*` paths resolve here. |
| `/var/lib/warrant-seller` | read-write volume | `IONET_STATE_DIR`: proposals and sessions. |
| `/run/secrets/seller.key` | read-only file | Seller transaction key, bare 64-hex. The manifest names it in `private_key_files.seller_key`. |
| `/tmp` | tmpfs | Temporary policy files. |

Nothing else is written at runtime, so the root filesystem can be read-only.

### Environment

| Variable | Notes |
| --- | --- |
| `MCP_AUTH_USER`, `MCP_AUTH_PASS` | HTTP basic auth for `/mcp`. Secret; env file only. |
| `WARRANT_MANIFEST` | Manifest path, for example `showcases/ionet_arc/config/mainnet-manifest.yaml`. |
| `WARRANT_RPC_URL` | Optional; overrides the manifest `rpc_url`. The RPC must answer at start. |
| `IO_NET_API_KEY` | Required on chain 5042. Secret; env file only. |
| `IONET_STATE_DIR` | Set by the image to `/var/lib/warrant-seller`. |
| `HOST`, `PORT` | Set by the image to `0.0.0.0` and `8000`. |

### Run

The hardening flags match the VM compose file:

```sh
docker run --rm --name warrant-seller \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true \
  -v "$PWD/scratch/config:/app/showcases/ionet_arc/config:ro" \
  -v "$PWD/scratch/state:/var/lib/warrant-seller" \
  -v "$PWD/scratch/seller.key:/run/secrets/seller.key:ro" \
  --env-file scratch/seller.env \
  -p 127.0.0.1:8000:8000 warrant-seller:dev
```

For a laptop smoke, start Anvil on loopback (`anvil`, which binds `127.0.0.1:8545`), and use a
scratch chain-31337 manifest whose `rpc_url` is `http://host.docker.internal:8545`. Docker
Desktop forwards `host.docker.internal` to the host loopback, so Anvil does not need
`--host 0.0.0.0`. On Linux Docker Engine, add `--add-host host.docker.internal:host-gateway` and
bind Anvil to the bridge address (`anvil --host 172.17.0.1`), not to every interface. Keep the
scratch manifest and key out of the checkout.

On chain 5042 the server refuses to start, exit code 1, in these cases:
* `IO_NET_API_KEY` is missing (`IO_NET_API_KEY is required on chain 5042`);
* `LOCAL_SERVER` is set;
* the manifest `chain_id` is not 5042;
* the RPC does not answer;
* `MCP_AUTH_USER` or `MCP_AUTH_PASS` is missing, empty or blank
  (`MCP_AUTH_PASS is required on chain 5042`).

On any other chain, the server refuses to start without both auth variables when `HOST` is not a
loopback address (`... required when binding the non-loopback host '0.0.0.0'`). The image sets
`HOST=0.0.0.0`, so the container always needs both variables.

### MCP handshake

The endpoint is `/mcp`. Responses are server-sent events: the JSON is on the `data:` line.

The credential never goes on the command line. `printf` is a shell builtin, and curl reads the
`user` line from a config on stdin (`-K -`). A password must not contain `"` or `\`.

```sh
U=http://127.0.0.1:8000/mcp
H='Accept: application/json, text/event-stream'
INIT='{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"smoke","version":"0"}}}'
mcp() {
  printf 'user = "%s:%s"\n' "$MCP_AUTH_USER" "$MCP_AUTH_PASS" |
    curl -s -K - -H "$H" -H 'Content-Type: application/json' "$@" "$U"
}

# 1. initialize: 200 and an mcp-session-id header
mcp -D headers.txt -d "$INIT"
SID=$(grep -i '^mcp-session-id:' headers.txt | cut -d' ' -f2 | tr -d '\r')

# 2. notifications/initialized: 202
mcp -o /dev/null -w '%{http_code}\n' -H "mcp-session-id: $SID" -H 'MCP-Protocol-Version: 2025-06-18' \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'

# 3. tools/list: 200
mcp -H "mcp-session-id: $SID" -H 'MCP-Protocol-Version: 2025-06-18' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'

# 4. initialize without auth: 401
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" -H 'Content-Type: application/json' -d "$INIT" "$U"
```

On chain 5042 the `initialize` instructions and the `propose_deployment`, `deploy_with_escrow`
and `submit_acceptance` descriptions start with the label
"after seller acceptance anyone can trigger payout; no proof; amounts up to 1 USD". On other
chains there is no label. `initialize` and `tools/list` make no io.net call.

The image has a port-only `HEALTHCHECK`. It sends no credential.
